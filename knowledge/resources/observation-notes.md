# 📘 Research Notes: M1 — Linux Fundamentals

> **Audience:** these notes are written for a learner on a **Mac** (Apple Silicon). They assume no
> prior Linux experience. Because a Mac runs macOS (its kernel is called **Darwin**), not Linux, every
> command in these notes is run inside a Linux guest that lives on the Mac — a **Docker Desktop**
> LinuxKit virtual machine running an **Ubuntu** container. The WSL2 path does not apply on a Mac and is
> not used here.

## 1. Objective

**What we are trying to achieve:**
Explain what actually happens between typing a command and seeing output, using the learner's own Mac-hosted Linux system as the evidence rather than a picture from a slide. Along the way, identify which kernel and which distribution the system is really running, understand why the filesystem shows more than just stored documents, and see what is running on the machine right now.

## 2. Core Concepts & Beginner Glossary

*A quick beginner's guide to the foundational terminology needed for this research. Each term is defined in plain language the first time it is used.*

- **Operating system (OS):** the layer of software that lets programs use the computer's hardware. Linux is an OS.
- **Kernel:** the central part of an operating system. It is the only part that directly controls the CPU, memory, disks, network, and other hardware. Every other program must ask the kernel to do hardware-related work.
- **Shell:** a program that reads commands typed by a person, works out what they mean, and asks the kernel to carry them out. Examples: `bash`, `zsh`, `fish`. The shell is software, not the keyboard or the screen.
- **Terminal emulator:** the app window that draws text and captures keystrokes (for example Terminal.app on a Mac, or GNOME Terminal in Linux). It is the display-and-input surface. It is **not** the shell.
- **Distribution (distro):** a complete Linux package — the Linux kernel plus utilities, a package manager, a default shell, configuration files, and often a desktop. Examples: Ubuntu, Debian, Fedora, Alpine.
- **Command:** an instruction typed into the shell, usually the name of a program to run (for example `uname`).
- **System call (syscall):** the controlled doorway a program uses to ask the kernel to do something only the kernel is allowed to do — read a file, get the time, read system information, allocate memory, open a network connection. The kernel checks permissions before acting.
- **Filesystem:** the way files and folders are organised and accessed. In Linux it is a single tree starting at `/` (the root).
- **Device node:** a special file in `/dev` that represents a piece of hardware or a pseudo-device, so ordinary file tools can read from and write to it.
- **Virtual (pseudo) filesystem:** a filesystem whose contents are generated by the kernel at the moment they are read and are not stored on disk. `/proc` and `/sys` are virtual filesystems.
- **Process:** a running program. Each process has a **PID** (process ID), a parent process, an owning user, and a command line.
- **PID:** the unique number the kernel assigns to a running process.
- **Darwin:** the name of the kernel inside macOS. It is a Unix-like kernel but it is **not** Linux. This matters on a Mac: running `uname -a` in the native macOS Terminal reports Darwin, not Linux.

## 3. Scope Research & Answers

### Theme 1 — Kernel, shell, and distro, and how a command travels to output

- **The Question/Topic:** What does each of the kernel, the shell, and the distribution do, and what happens between typing a command and seeing output? What is a system call, and why are the shell and the terminal emulator two different things?

- **The Detailed Explanation:**

  - **The kernel** is the core of the operating system and the only component with direct access to the hardware. It manages memory, decides which program gets the CPU next (this is called scheduling), manages disks and files, and communicates with devices. Ordinary programs cannot touch hardware directly; they ask the kernel to do it for them. The kernel is loaded into memory first when the system starts and stays there until the machine shuts down.

  - **The shell** is the interpreter a person talks to. It reads a typed line, splits it into words, expands things such as variables and wildcards, and then either runs the command itself (if it is a shell built-in) or starts the matching program as a new process. Common shells are `bash`, `zsh`, and `fish`.

  - **The distribution** is the complete software bundle built around the kernel: the kernel, system utilities, a package manager (for example `apt` on Ubuntu), a default shell, configuration files, and often a graphical desktop. Different distributions share the same Linux kernel family but differ in their defaults, which is why a command can behave differently from one distribution to another.

  - **How a typed command travels from the keyboard to the screen**, tracing the example `uname -a`:
    1. **Input:** the terminal emulator captures the keystrokes and sends the completed line to the shell.
    2. **Parsing:** the shell reads the line and breaks it into the command name (`uname`) and its argument (`-a`).
    3. **Lookup and execution:** `uname` is an external program, so the shell searches the directories listed in the `$PATH` environment variable to find it, then starts it as a new child process.
    4. **System calls:** the `uname` program cannot read system information on its own, so it makes a **system call** — it asks the kernel for that information. The kernel checks that the request is allowed, performs it, and sends the answer back to the program.
    5. **Output:** the program writes the result to *standard output* (`stdout`), which is connected back to the shell.
    6. **Display:** the shell passes the output to the terminal emulator, and the terminal emulator draws the characters on the screen.

  - **What a system call is, in detail:** a system call is the boundary between "user space" (ordinary programs, which are not allowed to touch hardware) and "kernel space" (the kernel, which is allowed to). When a program wants to read a file, check the time, get system information, or open a network connection, it cannot do so directly. It makes a system call: a specific, numbered request to the kernel. The kernel validates the request, carries it out using its privileged access to hardware, and returns the result. This single controlled doorway is what keeps an ordinary program from damaging the system.

  - **Why the shell and the terminal emulator are two different things:** the terminal emulator is the app that handles display and input — it draws the text and sends keystrokes. The shell is the program running *inside* that window that interprets commands. They are separate programs doing separate jobs. Changing the shell does not change the terminal, and changing the terminal does not change the shell. A common beginner mistake is to call the whole window "the shell", when in fact the window is the terminal emulator and the shell is what runs inside it. On a Mac, the app is Terminal.app (the terminal emulator) and the program running inside it is typically `zsh` (the shell).

### Theme 2 — System identity: kernel and distribution

- **The Question/Topic:** Which kernel and which distribution is the system actually running, where does the system report that about itself, and what do `uname -a` and `/etc/os-release` each report — and why are they not the same fact?

- **The Detailed Explanation:**

  - **On a Mac, the native terminal is the wrong place.** Running `uname -a` directly in macOS reports `Darwin`, because macOS is built on the Darwin kernel, not the Linux kernel. To examine a Linux system on a Mac, a Linux guest must be started first. The route used here is Docker Desktop, which runs a lightweight Linux virtual machine (built from a project called LinuxKit) and runs an Ubuntu container inside it. All commands below are run inside that Ubuntu container.

  - **Raw evidence — `uname -a` from the Ubuntu container:**
    ```text
    Linux 9ae51219e88a 6.12.76-linuxkit #1 SMP Mon Jul 27 16:56:11 UTC 2026 aarch64 GNU/Linux
    ```

  - **Raw evidence — `cat /etc/os-release` from the Ubuntu container:**
    ```text
    PRETTY_NAME="Ubuntu 26.04.1 LTS"
    NAME="Ubuntu"
    VERSION_ID="26.04"
    VERSION="26.04.1 LTS (Resolute Raccoon)"
    VERSION_CODENAME=resolute
    ID=ubuntu
    ID_LIKE=debian
    HOME_URL="https://www.ubuntu.com/"
    SUPPORT_URL="https://help.ubuntu.com/"
    BUG_REPORT_URL="https://bugs.launchpad.net/ubuntu/"
    PRIVACY_POLICY_URL="https://www.ubuntu.com/legal/terms-and-policies/privacy-policy"
    UBUNTU_CODENAME=resolute
    LOGO=ubuntu-logo
    ```

  - **The four facts, and exactly where each appears:**
    - **Kernel version — `6.12.76-linuxkit`.** This is the third field of the `uname -a` line, called the *kernel release*. The `-linuxkit` suffix shows the kernel was built for the Docker Desktop LinuxKit virtual machine, not for a bare-metal installation.
    - **Kernel architecture — `aarch64`.** This appears near the end of the `uname -a` line, in the *machine hardware name* field. `aarch64` means a 64-bit ARM processor, which is what an Apple Silicon Mac uses.
    - **Distribution name — `Ubuntu`.** This comes from the `NAME="Ubuntu"` field of `/etc/os-release` (also visible in `ID=ubuntu` and `PRETTY_NAME="Ubuntu ..."`).
    - **Distribution version — `26.04.1 LTS`.** This comes from the `VERSION="26.04.1 LTS (Resolute Raccoon)"` field. The machine-friendly short form `26.04` comes from the `VERSION_ID="26.04"` field. `VERSION` was chosen as the answer because it carries the fullest version detail, while `VERSION_ID` is the compact form scripts read.

  - **Why `uname -a` and `/etc/os-release` are not the same fact:**
    - `uname -a` asks the **running kernel** to describe itself. It reports the kernel name, the hostname, the kernel release and build date, the machine architecture, and the operating system name. It answers the question *"which Linux kernel is executing right now?"*
    - `/etc/os-release` is a **plain text file shipped by the distribution**. It reports the distribution's name, version, and branding. It answers the question *"which Linux distribution is installed?"*
    - These are independent. The file `/etc/os-release` is just a document on disk; it could be edited or replaced without changing the kernel at all. Meanwhile an administrator could upgrade or change the kernel without touching `/etc/os-release`. One describes the core of the system; the other describes the software bundle installed on top of it.

  - **Kernel versus distribution are independent facts (the Mac comparison):** On a Mac there is no WSL2, so the meaningful comparison is between a **shared-kernel container** and an **isolated virtual machine**. In the Docker Desktop setup used here, the Ubuntu container shares the LinuxKit virtual machine's kernel, so `uname -a` reports `6.12.76-linuxkit`. If the same Ubuntu were instead installed in an isolated virtual machine (for example Multipass), that VM would boot its **own** guest kernel, so the `uname -a` line would change — a different kernel release and build. The `/etc/os-release` file, however, could stay exactly the same, because the distribution image is unchanged. This shows that changing the environment changes the **kernel** independently of the **distribution**. The kernel is what actually ran the machine; the distribution is the software bundle on top of it.

### Theme 3 — The filesystem as an abstraction

- **The Question/Topic:** Linux exposes hardware, running processes, and configuration as entries in the filesystem. What lives in `/dev` and `/proc`, and what does "everything is a file" mean in practice?

- **The Detailed Explanation:**

  - **What "everything is a file" means in practice:** in Linux, many resources that are not ordinary documents are still presented as entries in the filesystem tree, so the same tools — `cat`, `ls`, reading, writing — work on all of them. Concretely:
    - **Regular files** such as `/etc/os-release` or `/etc/passwd` are ordinary documents stored on disk.
    - **Directories** are themselves a special kind of file.
    - **Device nodes** in `/dev` represent hardware and pseudo-devices, so hardware can be read and written like a file.
    - **Kernel interfaces** in `/proc` and `/sys` expose live system state as files.
    - **Pipes and sockets**, used for programs to talk to each other, are also represented through file descriptors.
    It is not literally true that *every* single thing is a file, but the design principle is real and useful: by treating input and output uniformly, one set of tools can reach disk files, hardware devices, and live kernel information.

  - **What lives in `/dev`:** `/dev` holds **device nodes** — special files that stand in for hardware and pseudo-devices. Examples:
    - `/dev/sda` — a disk drive.
    - `/dev/null` — a "black hole" that discards anything written to it and returns nothing when read.
    - `/dev/zero` — produces an endless stream of zero bytes when read.
    - `/dev/random` and `/dev/urandom` — provide random data.
    - `/dev/tty*` — represent terminals.
    - `/dev/stdin`, `/dev/stdout`, `/dev/stderr` — represent a program's standard input, output, and error streams.
    When a program reads or writes one of these files, it is really talking to the kernel driver that controls the underlying device.

    *Capture the real output from the container:*
    ```text
    ls /dev | head -15
    ```

  - **What lives in `/proc`:** `/proc` is a **virtual (pseudo) filesystem** created by the kernel at runtime. Nothing inside it is stored on disk; the kernel generates each file's contents the moment it is read. Examples:
    - `/proc/cpuinfo` — details about the CPU.
    - `/proc/meminfo` — details about memory.
    - `/proc/version` — the running kernel's version.
    - `/proc/uptime` — how long the system has been running.
    - `/proc/<pid>/` — one folder per running process, containing files such as `cmdline` (the command that started it), `status` (its state), and `fd` (the files it has open).
    Because these files are generated live, reading them gives a current snapshot of the system, not a stored record.

    *Capture the real output from the container:*
    ```text
    cat /proc/version
    cat /proc/cpuinfo | head -5
    ls /proc | head -10
    ```

  - **The filesystem as an abstraction over physical storage:** The directory tree — `/`, `/etc`, `/home`, `/usr`, `/dev`, `/proc`, `/var`, and the rest — is an abstraction laid on top of physical storage. The real underlying storage consists of blocks on a disk or SSD, organised by a filesystem such as ext4 or XFS. The kernel's **Virtual File System (VFS)** presents all of this as one unified tree. Importantly, the virtual filesystems `/proc`, `/sys`, and `/dev` have **no disk blocks behind them at all**; their contents reflect live kernel state. This is why what is visible in the tree is not always the same as what is stored on disk.

### Theme 4 — A live system

- **The Question/Topic:** What is running on the machine right now, how are running processes listed, and what does the kernel have to do with them? Where does reality differ from what was expected before looking?

- **The Detailed Explanation:**

  - **How to list running processes:** the shell provides several tools for this:
    - `ps aux` — a one-time snapshot of all processes, in the BSD style.
    - `ps -ef` — a one-time snapshot, in the POSIX style.
    - `top` — a live, continuously updating view; press `q` to quit.
    - `htop` — a friendlier interactive view (may need to be installed first).
    - `pgrep` or `pidof` — find a specific process by name.

    *Capture the real output from the container:*
    ```text
    ps aux | head -15
    top -b -n 1 | head -20
    ```

  - **What the kernel has to do with processes:** the kernel is responsible for creating processes, scheduling them (deciding which one runs on the CPU next, and for how long), giving each process memory, and terminating them. Every process has a PID, a parent process, an owning user, and a command line. The shell itself is a process; when a command such as `uname` runs, the shell starts it as a child process, and that child makes system calls to the kernel to do its work.

  - **What differs from expectations (observed on this system):** the container is deliberately minimal, so only a small number of processes appear. `ps aux` shows the shell (`bash`) and the command currently running, with very little else. This is a genuine surprise for a beginner used to a desktop machine, where dozens of background services always run. A container is built to be small and to do one job, so it has no full init system, no desktop session, and no background service sprawl. Inside a container, PID 1 is typically the shell or the container's entry point, not a complete init system. The kernel still owns scheduling and memory in full; the container simply does not package the usual user-space management layer around it.

## 4. Key Takeaways & Common Traps

- **The Big Picture:** kernel and distribution are two separate facts. The kernel is the core that actually controls the hardware, while the distribution is the software bundle installed on top of it. On a Mac, the Linux kernel only appears inside a guest (here, Docker Desktop's LinuxKit VM running Ubuntu); the native macOS terminal reports Darwin, which is not Linux.

- **Common Beginner Trap:** running Linux commands in the **native macOS Terminal** and trusting the result. `uname -a` there reports `Darwin`, and other commands behave like their BSD/macOS versions rather than their Linux versions. On a Mac, a Linux guest must be started first (for example `docker run -it ubuntu /bin/bash`) before any Linux claim can be verified. A second common trap is confusing the **terminal emulator** (the window) with the **shell** (the program running inside it) — they are different programs doing different jobs.
